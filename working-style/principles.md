## 编号规则

- 编号 `P1`、`P2`…**固定不复用**。原则作废就把 `status` 改为 `superseded`，编号保留，后面的不重排。
- **编号小的优先于编号大的**。冲突时 Agent 按编号顺序裁决，并在交付里说明用了哪条。
- 一条原则 = 一句可执行的判断 + 最多两句说明。写不出「所以该怎么做」，就不是原则，是感想。

## 原则该怎么长出来

不靠一次访谈，靠反复观察。以下三种信号出现时才新增一条：

1. **同一件事被否两次** —— 说明有一个我没说出口的标准
2. **同一个取舍在两个项目里重复** —— 说明是稳定的价值排序，不是临时判断
3. **本人主动说出「以后都这样」** —— 直接记为 `high`

只出现一次的叫 `exception`，记到 `memory/log/` 里，不要升级成原则。

## 常见原则的候选维度（供本人确认时对照，不必全填）

| 维度 | 典型冲突 |
|------|----------|
| 速度 vs 完备 | 先交付 80% 可用的，还是等 100% 再给 |
| 自主 vs 确认 | 自己拍板还是先问 |
| 复用 vs 从简 | 抽成通用组件还是就地写死 |
| 一致 vs 更优 | 沿用旧约定还是引入更好的做法 |
| 显式 vs 简洁 | 多写配置和注释，还是保持最少代码 |
| 深度 vs 广度 | 一个方向做透，还是先铺开验证 |
